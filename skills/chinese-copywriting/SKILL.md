# 中文文案排版

依《中文文案排版指北》統一中文文案的排版用法。

## 定位

只管**排版層**：空格、全形半形、標點形制、名詞寫法。

不動字句與內容。錯別字、文句潤飾、去除 AI 痕跡、翻譯都不屬於這裡的職責，遇到就說明並交給對應的工具。

## 模式一：校對

**絕不自動改檔，也絕不未經確認就開跑。** 校對對象與修正處置都要在動手前一次問清楚。

### 步驟 0：開跑前確認

跑腳本之前先用 `AskUserQuestion` 一次問完三件事，取得答覆才進步驟 1。

**問題一：校對哪個檔？** 預設值取**編輯器當前開啟的檔案**（`ide_opened_file` 或 `ide_selection` 指到的路徑），把它放在第一個選項並標示「（當前開啟）」。使用者訊息已明確指定路徑時直接用那個，不必問。沒有當前開啟的檔案也沒有指定路徑就直接問要校對哪個檔，不要自行猜測。

**問題二：查完要怎麼處理？** 四個選項：

- **自動修正可安全處理的項目** — 跑 `--fix` 修 `fixable` 為 `true` 的項目，改完回報 diff 摘要；裁決保留的與補掃找到的另附建議清單，不動檔
- **全部修正** — 先跑 `--fix`，接著把**裁決保留的 `low` 項與補掃找到的全部項目**（規則 9、10 的名詞與縮寫、認可類單位的空格、英文書名改斜體）用 `Edit` 逐處改掉。判定為「建議」的也一併修，但要在回報裡單獨列出來，讓使用者知道哪幾處是憑規範判的
- **只出報告，不改檔** — 報告落地到 `docs/chinese-copywriting/`，見〈報告落地〉，回覆只給路徑
- **先看清單再決定** — 在對話裡出完報告停下來，等使用者指定編號才改；這一項不寫檔

**問題三：要不要擴充英文單位？** 腳本內建的 `UNITS` 只有 23 個，刻意收得窄。三個選項：

- **不擴充（預設）** — 漏掉的單位由步驟 3 的補掃處理
- **帶入常見的資訊與電子單位** — `kHz,ms,μs,GiB,MiB,mAh,nm,dB,mV,kW,mmHg,kPa,mol,kcal`，取自 [references/terminology.md](references/terminology.md) 的認可類
- **自訂** — 使用者自己列，逗號分隔

答覆帶進 `--units`。**擴充的單位一律標 `low`、不自動修**，因為單位縮寫跟英文寫法大量重疊，正則分不出來，要靠步驟 2 裁決。

爭議規則預設不查；使用者明確要求才加 `--dispute`。

### 步驟 1 起：執行

規則層負責掃描與定位，模型負責裁決與補漏。兩層各做各的，不互相覆寫。

1. 跑檢查腳本取得機械式違規清單：

   ```bash
   python3 skills/chinese-copywriting/scripts/check_copywriting.py --json <file>
   ```

   步驟 0 有答覆要擴充單位就加 `--units kHz,ms,mAh`。

2. **裁決**：只處理 `confidence` 為 `low` 的那幾筆。逐筆讀原文前後各兩行，判 keep 或 drop，drop 要寫理由。**不得回頭推翻 `high` 的判定**，那些是純字元層的事實。三種 `low` 各有各的看法：

   - **R6 的引號與括號** — `呼叫 setState() 之後` 這種括號屬於程式碼寫法而非中文標點
   - **R8** — 判斷那段到底是不是完整的英文整句
   - **`--units` 帶進來的單位** — 數字後面接的到底是量測值還是產品代號。`5G`、`4K`、`3in1`、`2T` 跟 `3bar`、`65W`、`24h` 在正則眼裡一模一樣，只有上下文分得出來。辨識準則見 [references/terminology.md](references/terminology.md) 的〈單位與英文寫法的重疊〉
3. **補掃**：先讀 [references/terminology.md](references/terminology.md)，**每一筆候選都要先過白名單再判定**——命中豁免類就不報，命中認可類就依規則 3 補報空格。範圍是規則 9、10，以及腳本結構上抓不到的：非 `UNITS` 表列的各領域單位、CJK 擴充區漢字貼著英文、沒有引號包住的英文整句、英文書名該用斜體而非中文書名號。表外的名詞一律標「建議」。
4. 合併步驟 1 至 3 的結果，依〈報告樣板〉輸出「排版違規清單」，每條都要帶引用參考。
5. 依步驟 0 談好的處置方式執行。選「全部修正」時，補掃找到的項目一個都不能漏；`--fix` 會改動行內容，所以接下來的 `Edit` 要以**修正後的檔案**重新定位，不要拿步驟 1 記下的原文片段去比對。選「先看清單再決定」就停在清單等指示。
6. 沒有違規就直接回報通過，不必再問。

**規則書的反例由腳本標記，不必自己判。** 校對排版規則文件（例如本專案的 `README*.md`、`references/rules.md`）會大量命中 `錯誤：` 底下的示範句，那些是刻意寫錯的教材。腳本把它們標成 `in_example: true` 且 `fixable: false`，回報時放進「不予修正」那節。

改檔後必須回報實際改動筆數與 diff 摘要。

## 模式二：撰寫

產出中文文案時直接套用 [references/rules.md](references/rules.md) 的規則，不輸出報告、不詢問、不附引用參考。寫完自我檢查一遍空格與全半形。

## 規則與引用來源

規則本體、行號引用、例外與爭議規則全部在 [references/rules.md](references/rules.md)：

- **規則索引**：12 條規則的名稱、上游行數、所屬章節
- **例外索引**：5 條例外各自對應哪一條規則、出自哪幾行
- **規則細則**：每條的完整正誤範例

校對前先讀那份，不要憑記憶引用行號。

規則 9、10 的判定依據，以及補掃時要先過的白名單，在 [references/terminology.md](references/terminology.md)：判定順序、三級結論、豁免類與認可類白名單、分領域名詞對照表。那份是規範不是窮舉表，查不到不等於寫錯。

爭議規則（11、12）預設不套用也不報違規，使用者明確要求才加 `--dispute`。產品名詞的豁免清單在 `scripts/check_copywriting.py` 頂端的 `EXCEPTION_TERMS`，遇到新的官方名詞就加進去；那份是給腳本用的，與 terminology.md 各自維護。

## 引用規範

**每一條違規都要附引用參考，指回唯一事實根據**：

<https://github.com/sparanoid/chinese-copywriting-guidelines/blob/master/README.md>

格式是規則名稱接行數，中間一個半形空格：

```text
{規則名稱} L{起始行}-L{結束行}
```

例如 `數字與單位之間需要增加空格 L52-L74`、`使用全形中文標點 L118-L136`；只涉及單行時寫成 `L38`。行數一律查 [references/rules.md](references/rules.md) 的索引，不要自行推算。

引用的是規則所在的那幾行，不是違規文字所在的行——違規位置寫在清單的行號欄。

## 報告樣板

校對結果照這個結構輸出，欄位不增不減。樣板本身也遵守上列規則：

```markdown
## 排版違規清單

來源基準：sparanoid/chinese-copywriting-guidelines README.md（commit `bd7873c`）

| 行號 | 規則 | 原文片段 | 建議修正 | 引用參考 | 來源 | 判定 | 可自動修正 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| L30 | R1 | `在LeanCloud上` | `在 LeanCloud 上` | 中英文之間需要增加空格 L22-L38 | 腳本 | 違規 | 是 |
| L60 | R3 | `10Gbps` | `10 Gbps` | 數字與單位之間需要增加空格 L52-L74 | 腳本 | 違規 | 是 |
| L74 | R3 | `44.1kHz` | `44.1 kHz` | 數字與單位之間需要增加空格 L52-L74 | AI | 違規 | 否 |
| L182 | R9 | `Github` | `GitHub` | 專有名詞使用正確的大小寫 L166-L198 | AI | 違規 | 否 |
| L204 | R10 | `Vitepress` | `VitePress` | 專有名詞使用正確的大小寫 L166-L198 | AI | 建議 | 否 |

## 不予修正

| 行號 | 內容 | 理由 |
| --- | --- | --- |
| L128 | `嗨! 你知道嘛?` | 規則書反例 |
| L92 | `呼叫 setState() 之後` | 裁決駁回：括號屬程式碼寫法，非中文標點誤用 |
| L110 | `MRI 影像` | 白名單豁免：醫學領域公認縮寫 |

## 可補進規範的候選

| 名詞 | 建議寫法 | 來源 | 領域 |
| --- | --- | --- | --- |
| Vitepress | VitePress | vitepress.dev 官網 | 軟體開發 |
```

「來源」欄分 `腳本` 與 `AI`；「判定」欄分 `違規` 與 `建議`，判定為建議的一律不自動修。

沒有違規時只回報通過與所依據的來源基準，不輸出空表格。「不予修正」與「可補進規範的候選」兩節沒有內容就整節省略。

## 報告落地

選「只出報告，不改檔」時，報告寫成檔案而不是貼在對話裡。路徑由腳本產生，不要自己拼：

```bash
bash skills/chinese-copywriting/scripts/new_report.sh <原檔路徑>
```

它會建好 `<專案根>/docs/chinese-copywriting/`、第一次建立時補上一份 `.gitignore` 擋掉版控，然後把報告檔的完整路徑印出來。檔名格式是 `{年月日}-{時分秒}-{原檔案名稱}.{副檔名}`，例如 `20260831-232114-README.md`。

報告內容分兩段：

1. 〈報告樣板〉那三節，欄位不增不減
2. `## 完整修正後文稿`，底下放整份改好的內容，讓使用者可以直接取用

寫完只回覆報告路徑，不要把清單或文稿再貼一次到對話裡。

## 腳本

兩支，都在 `scripts/`：`check_copywriting.py` 做檢查與修正，`new_report.sh` 產生報告落地路徑（見〈報告落地〉）。

```
check_copywriting.py [--fix] [--json] [--dispute] [--units U1,U2] <file>...
```

- 不帶旗標：只報告，有違規時 exit code 為 1
- `--fix`：就地修正規則 1、2、3、4、5、7；規則 6、8、9、10 一律只報告
- `--json`：機器可讀輸出
- `--dispute`：一併檢查爭議規則
- `--units`：擴充規則 3 的單位表，逗號分隔。內建的 23 個是篩過的，帶進來的沒有，所以一律標 `low`、不自動修

`--json` 每筆違規帶這幾個欄位：

| 欄位 | 意義 |
| --- | --- |
| `confidence` | `high` 是純字元層、無歧義；`low` 是規則命中但要看上下文，交步驟 2 裁決 |
| `in_example` | `true` 表示落在規則書「錯誤：」底下的反例區塊，是刻意寫錯的教材 |
| `fixable` | 三個條件的合取：規則在 `FIXABLE` 內、`confidence` 為 `high`、且 `in_example` 為 `false` |

`--fix` 只動 `fixable` 為 `true` 的項目。拿不準的與規則書反例都不會被碰到，所以直接對規則書本身跑 `--fix` 是安全的。

腳本會自動跳過 fenced code block、縮排程式碼、行內程式碼內容、URL、Markdown 連結目標、HTML 標籤屬性與 YAML frontmatter。

腳本本身不做互動確認，這樣才能進 CI。**取得使用者同意前不得帶 `--fix`。**
